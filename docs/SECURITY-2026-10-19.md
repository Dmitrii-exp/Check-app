# Check App: security fixes, 19 October 2026

The production database and Robokassa callback were updated. The existing web
and Android clients continue to use their existing API, authentication flow,
plan names and prices. No customer subscriptions, roles or stored history were
changed by the migrations.

## Payment confirmation

`robokassa-result` now starts successfully, validates the amount and invoice
format, rejects duplicate/ambiguous parameters and verifies the live signature
before calling a server-only RPC. Test signatures are acknowledged without
changing real entitlements. Signature comparison uses a constant-time primitive.

`process_verified_robokassa_payment` locks the order and company, updates the
subscription and marks the order paid in one database transaction. Replayed
notifications return `already_paid` without extending the term. Different orders
for the same company are serialized. A renewal of the same plan preserves the
remaining time and adds one calendar month in UTC. Clients cannot execute this
RPC or write payment orders, subscriptions, super-admins or unlimited grants.

## Authorization and data integrity

- Existing company owners are protected from client-side deletion, demotion or
  replacement. A manager can appoint or remove a department lead, but cannot
  create another company owner by updating or upserting a profile. Registration
  and invitation RPCs retain their intended access.
- Employees cannot delete equipment, maintenance definitions, tasks, history or
  submitted report photos. Department leads retain structural management within
  their department; report corrections and deletions require the company owner.
- A worker can submit a report for an accessible, unfinished task. The database
  requires their authenticated author ID, worker name and an uploaded photo.
  Assignment and company/department/equipment relationships are validated.
- Employees may generate only due recurring maintenance tasks from existing
  templates. Task definition changes, forged completion states and reporting
  another worker's assigned task are denied.
- Quotas and frozen equipment/departments are checked in the database using a
  stable `created_at, id` order. Identity and creation time cannot be rewritten
  to change that order. Per-company advisory locks serialize quota/report checks.
- An expired paid subscription prevents new task execution and reports. Stored
  history remains readable. Frozen objects stay visible for reference; meaningful
  updates and use in new operational records are rejected. Unchanged upserts
  remain accepted for the existing manager synchronization flow.
- Photo access is restricted to the company and accessible department or task.
  Workers can clean up their own unreferenced uploads but cannot remove a
  submitted report image. Equipment photos accept JPEG, PNG or WebP up to 5 MiB.
- Subscription reads are allowed to company members so worker sessions load
  the real plan; payment management remains restricted to the manager.

The migration timestamps match production migration history. These are
incremental migrations for the existing Check App schema, not a fresh database
bootstrap. The website deployment workflow does not apply them automatically.

## Validation

```sh
node supabase/tests/payment-http.test.mjs
```

The SQL integration suites `supabase/tests/payment-transaction.sql` and
`supabase/tests/permissions-transaction.sql` were run against production after
deployment, within explicit transactions ending in `ROLLBACK`. They use generated
fixture IDs, synthetic users and metadata only; no customer record or real
payment is used. A database owner connection is required to run these suites.

Covered checks include payment replay, wrong amount, private RPC privileges,
forged/test callbacks, company isolation, role/subscription escalation, quota and
freeze bypass, worker photo-report completion, history/photo deletion, department
lead assignment, registration, invitation and compatibility with unchanged owner
upserts. The live callback rejected a forged signature with HTTP 403, replacing
the previous HTTP 503 boot failure.

No real purchase or charge was initiated. The complete browser checkout and bank
confirmation flow was not exercised.

## Remaining configuration notice

Supabase's leaked-password protection is still disabled; no Auth configuration
write capability is exposed by the connected management tools. Enable it in
Authentication settings if the project's plan supports it. Remaining advisor
notices about authenticated SECURITY DEFINER functions refer to the existing
registration, company-context and guarded super-admin RPCs. Their authorization
checks were preserved; the new privileged payment RPC is server-only and new
authorization helpers are outside the exposed public API schema.
